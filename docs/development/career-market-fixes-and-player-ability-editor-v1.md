# 계약 시장 경계 수정 · CA/PA 표시와 선수 편집 V1

2026-09-07. 기준 HEAD: `2ad8c20453e3c5338ed02ca5ca515390d75a6a25`.
사용자가 승인한 Zeus·ShowMaker 능력치 상향 작업에 계약 시장 결함 2건과 CA/PA 편집 기반을 합쳤다. 커밋·푸시·배포는 수행하지 않았다.

## 실제로 가능해진 일

- Career 화면 상단의 **선수 CA·PA 비교 및 새 Career 데이터 편집**을 열어 460명을 검색하고 CA 순으로 비교한다.
- 선수별 포지션에 맞는 능력치 12개와 PA를 편집하고 저장한다. 챔피언 숙련도도 함께 확인한다.
- 생성된 Career의 선수 명부에서는 해당 Career에 저장된 능력치로 CA를 계산하고 저장된 PA를 표시한다. CA 정렬 및 상세 능력치·숙련도 조회를 함께 제공한다.
- 편집 후 생성하는 Career는 변경한 12개 능력치를 국내·해외 시즌 선수 입력과 계약 시장의 기량 평가에 사용한다.
- 결정일 직전 수정한 거래도 상대 AI 구단의 검토를 거쳐 공통 결정에 참여한다. 관련 없는 기간의 임대로 계약이 잘못 차단되는 문제를 수정했다.

## CA · 스카우팅 · AI · 가격 · PA 정책

| 대상 | 이번 구현 |
|---|---|
| 표시 CA | `round(1 + (능력치 합계 - 12) × 199 / 228)`. 역할별 12개 동일 비중, 최종 한 번 반올림. 모두 1이면 CA 1, 모두 20이면 CA 200. |
| 스카우팅 비교 | Career 명부 및 새 Career 데이터 화면에서 CA를 비교하고 12개 상세 능력치와 챔피언 숙련도를 함께 조회. 별도 스카우팅 인력·불확실성·조사 일정은 구현하지 않음. |
| AI 영입 | `PlayerAbilityPolicy.strength`의 원래 능력치 합계로 현재 기량 평가. 기존 포지션 공백·주전 대비 개선·역할·선수 의사·예산·등록 자격 판단을 유지. 표시 CA의 정수 반올림과 PA는 입력하지 않음. |
| 연봉·가격 | 동일한 원래 기량 합계 × 1,000을 기준 연봉으로 사용. 잔여 계약 기간에 따른 가치, 판매 프리미엄/불만/체불, 구매 필요와 지불 여력, 실제 합의 가격 구분을 유지. 이번 CA 추가 때문에 기존 가격 척도를 다시 보정하지 않음. |
| PA | 사용자 작성값을 `playerId`로 연결해 저장·표시. 평생 능력 천장이라는 의미이며 이번에는 성장·AI·가격·경기 입력에 사용하지 않음. CA보다 낮아도 임의로 상향하거나 CA를 낮추지 않음. 미입력은 null. |

새로 도입한 것은 기량 평가의 공통 진입점과 표시·편집이다. 기존 AI를 CA 한 숫자로 대체하거나 새로운 영입 효용식을 추가한 작업은 아니다.

승인된 기본 데이터는 Zeus 합계 **225 / CA 187 / PA 197**, ShowMaker 합계 **222 / CA 184 / PA 196**다. PA는 사용자 원본 그대로 가져온다. 두 선수 상향 전후 12개 항목은 [별도 기록](zeus-showmaker-ratings-adjustment-2026-09-07.md)에 있다.

## 결함 수정

### 결정 직전 역제안

기존 거래는 수정 제출일 + 2일을 응답일로 잡으면서 AI 구단 응답을 결정일 전까지만 처리했다. 따라서 결정일 1~2일 전 수정안은 검토 기회를 잃을 수 있었다.

응답일을 공통 결정일 이내로 제한하고 결정 당일의 예정된 AI 구단 응답을 선수 결정보다 먼저 처리한다. 공통 결정일, 적용일, 최대 협상 단계는 유지한다. 사용자가 관리하는 구단의 동의를 자동으로 대신하지 않는다. 사용자는 날짜를 넘기기 전에 동의해야 하며, 미합의 거래가 결정 단계에서 탈락하는 기존 규칙은 유지한다.

### 임대로 인한 명부 상한 오판

기존 상한 검사는 모든 임대 시작·반환 날짜를 검사 집합에 넣고 새 선수를 각 날짜에 더했다. 새 계약 시작 전이나 종료 후의 명부까지 검사해 관련 없는 임대로도 정상 제안이 차단될 수 있었다.

검사 날짜를 신규 계약의 시작~종료 구간으로 제한한다. 해당 구간 안의 기존·예정 계약, 열린 제안, 임대 입단과 동의한 거래는 계속 포함한다. 실제 겹치는 임대로 상한을 넘는 경우는 계속 거절한다.

## 저장과 적용 범위

- PA 원본 `선수정보/포텐/runtime/player-potential-ability-v2.json`을 backend 리소스로 바이트 그대로 복사했다. 460개 ID가 선수 카탈로그 전체와 정확히 일치하며 중복·범위 오류가 없음을 로더가 검사한다.
- V18은 편집 revision, 선수별 override, 명령 receipt용 테이블 3개를 추가한다. 기존 Career 테이블과 저장된 directory를 일괄 수정하지 않는다.
- API는 `GET /api/v1/player-data`, `POST /api/v1/player-data`. POST는 `playerId`, 12개 `ratings`, `potentialAbility`, `expectedRevision`, `clientCommandId`를 받는다.
- 소수·누락 항목·다른 포지션의 능력치·범위 초과·알 수 없는 ID·중복 JSON 필드를 거절한다. `playerId`, 포지션, 숙련도, 소속은 편집으로 바꾸지 않는다.
- 전역 편집 revision 잠금으로 변경과 새 Career의 전체 선수 snapshot을 일관되게 처리한다. 동일 UUID·동일 내용 재전송은 원래 receipt를 반환하고, 다른 내용 또는 오래된 revision은 409로 처리한다.
- 편집 자료는 새 Career의 생성 transaction에서 directory 및 시즌 로스터로 복사하고, 이어서 계약 시장을 초기화한다. 국내 미시작 경기의 실제 선수 입력에도 동일한 저장값을 전달한다.
- 이미 생성한 Career와 진행 중인 Series는 이후 편집의 영향을 받지 않는다. 재시작 복구·조회·다음 시즌 이월에서도 편집 카탈로그를 다시 import하지 않는다.
- 원본 파일을 POST 요청으로 덮어쓰지 않는다. 앱 편집은 해당 DB에 보관되므로 다른 DB/설치에 대한 편집 내보내기·가져오기는 후속 범위다.

**기존 저장 호환의 한계:** 이번 기본 Zeus/ShowMaker 리소스 교체 이전에 만든 Career는 기존 카탈로그 해시 검사 때문에 로드가 차단된다. 사용자가 명시적으로 새 Career만 적용하고 기존 저장 호환은 후속으로 남기기로 선택했다. 반면 이번 버전에서 생성한 Career는 편집기의 DB override를 다시 변경해도 기본 리소스 해시가 바뀌지 않으므로 계속 로드할 수 있다.

## 검증과 실행 비용

- 선행 상향 작업: 카탈로그·참조 API **3 suites / 37 tests 통과**, 2분 57초.
- 선행 전체 회귀는 사용자의 범위 변경과 중단 요청에 따라 중단했다. 완료 또는 성공한 전체 회귀로 주장하지 않는다. 그 과정에서 확인한 이전 리소스 묶음 해시 고정과 Career 참조 해시 기대값을 수정했다. 무결성 검사를 제거하지 않았다.
- 계약·CA·편집 집중 실행: **2 suites / 39 tests**, 실패·오류·skip 0, **5분 53초**. 최초 명령의 잘못된 이주 메서드 selector는 실행 증거로 계산하지 않았고, 다음 실행에서 정확한 메서드를 지정했다.
- 경기 입력·이주 후속 실행: **6 suites / 7 tests**, 실패·오류·skip 0, **3분 14초**. 두 실행의 합계는 46건 실행이며 편집 API 1건을 보강 후 다시 확인했다.
- 후속 7건: 새 Career의 실제 eligiblePair 입력, 파일 DB 이주/재시작 2건, 입력 provenance 및 동일 seed 2건, 기존 실제 Auto BO3·Player BO1 경로, 실제 Player Draft 경기 경로.
- `npm run career:verify`: **66 scenarios 통과**. `npm run build`: **167 modules 통과**.
- 실제 브라우저: 전용 `/tmp` DB에서 Zeus의 메카닉 20→19, PA 197→190을 시험해 CA 187→186과 저장 메시지를 확인했다. 이는 테스트 DB에만 한 변경이며 배포할 기본 값은 Zeus CA 187 / PA 197이다.
- 서버 저장 후 응답만 차단하고 브라우저를 새로고침했다. 보관한 원본 UUID로 receipt를 복구하고 저장 화면이 다시 활성화됨을 확인했다. 첫 네트워크 주입 스크립트는 라우트 해제 시점이 빨라 실패하여, 차단 완료를 기다리는 방식으로 교정했다.
- 전체 회귀를 다시 실행하지 않았다. 사용자 요청에 따라 변경한 순수 규칙, 저장/API, 직접 소비하는 경기 입력과 대표 실행 경로를 선택했다. 새로운 skip/제외 규칙, 대규모 seed·밸런스 진단은 추가하지 않았다.
